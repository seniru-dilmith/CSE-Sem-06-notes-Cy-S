> [!abstract] 
> This note covers the evolution and mechanics of implementation support in Human-Computer Interaction (HCI). It explores how programming models have developed over the years to translate design concepts into functional interfaces, moving from hardware-specific coding to high-level layers of abstraction like <span style="color: #1976d2; font-weight: bold;">Windowing Systems</span>, <span style="color: #388e3c; font-weight: bold;">Interaction Toolkits</span>, and <span style="color: #f57c00; font-weight: bold;">User Interface Management Systems (UIMS)</span>.

---
## 1. Introduction to Implementation Support

Implementation support focuses on the tools and levels of services provided to programmers to create interfaces and handle interactions. In the early days (70s and 80s), programming was largely backend-oriented. As <span style="font-weight: bold;">Graphical User Interfaces (GUIs)</span> emerged in the 90s, the challenge shifted toward managing mouse, keyboard, and display interactions.

### The Evolution of Abstraction
Initially, programming was <span style="color: #d32f2f; font-weight: bold;">hardware-specific</span>. For instance, in older C/C++ implementations, arithmetic or floating-point calculations could differ between compilers and machines. Over time, these have evolved into <span style="color: #7b1fa2; font-weight: bold;">interaction-technique-specific</span> tools.

> [!info] 
> <span style="font-weight: bold;">Levels of Abstraction:</span> Modern development utilizes a layer of abstraction where programmers no longer worry about underlying implementations. They simply call an <span style="font-weight: bold;">API</span> or library to execute complex interface tasks.

> [!question] FAQ
> **Q: What are the main levels of development tools for implementation support in HCI?**
> **A:** The main layers of development tools that provide programming support are windowing systems, interaction toolkits, and User Interface Management Systems (UIMS).

## 2. Windowing Systems

A windowing system is the core support for separate and simultaneous user-system activity. It acts as a placeholder for multiple instances of programs.

### The Atomic Unit: The Pixel
The most atomic part of a window is the <span style="color: #e64a19; font-weight: bold;">Pixel</span> (Picture Element). You cannot conceptually work with half a pixel; it is the fundamental unit of resolution and coordinate systems (Cartesian coordinates).

### Core Roles of a Windowing System
1. <span style="font-weight: bold;">Device Independence:</span> It abstracts the hardware. Programmers interact with an "abstract terminal" rather than specific hardware drivers.
2. <span style="font-weight: bold;">Resource Sharing:</span> It manages how multiple applications share the screen and input devices without causing confusion.

![[Pasted image 20260516003021.png]]

> [!example] 
> If you place a window in the center of the screen, the system ensures those specific pixel resources are not used by other background processes, linking the visualization directly to the application process.


> [!question] FAQ
> **Q: What are the core elements and roles of a windowing system?**
> **A:** A windowing system provides core support for separate and simultaneous user-system activity. Its two main elements are:
> - **Device independence:** It programs the abstract terminal, manages device drivers, and handles image models (pixels, PostScript, GKS, PHIGS).
> - **Resource sharing:** It achieves simultaneity of user tasks by supporting independent processes and isolating individual applications.

### Windowing Architectures
There are three primary ways to architect these systems:

| Architecture                                          | Description                                          | Pros/Cons                                                                      |
| :---------------------------------------------------- | :--------------------------------------------------- | :----------------------------------------------------------------------------- |
| <span style="font-weight: bold;">App-Managed</span>   | Each application manages all its own processes.      | <span style="color: #d32f2f;">Difficult.</span> High synchronization overhead. |
| <span style="font-weight: bold;">Kernel-Based</span>  | Management role is within the OS kernel.             | Applications are tied to a specific OS (e.g., early Windows/Linux).            |
| <span style="font-weight: bold;">Client-Server</span> | Management is a separate application outside the OS. | <span style="color: #388e3c;">Maximum Portability.</span> Used by X Windows.   |

> [!important] 
> The <span style="font-weight: bold;">Client-Server Architecture</span> (like X Windows) allows for thin layers of interaction. The server handles the resources, while the client handles the application logic.


> [!question] FAQ
> 
> **Q: How does the X Windows Architecture function?**
> 
> **A:** It utilizes a client-server architecture with a pixel imaging model. The X protocol defines server-client communication. A separate window manager client enforces policies for I/O, such as input focus, tiled vs. overlapping windows, and inter-client data transfers.

## 3. Programming the Application (Dialogue Control)

Dialogue control refers to how the system handles the conversation between the user and the application.

### Two Main Paradigms

#### 1. Read-Evaluation Loop (Internal Control)

![[Pasted image 20260516003654.png]]

A continuous loop that "listens" for events.

- Downside: Extremely resource-intensive as it consumes CPU cycles even when nothing is happening.
    
- Upside: Simple to implement for sequential interactions.
    

#### 2. Notification-Based (External Control)

![[Pasted image 20260516003609.png]]

The application registers Callbacks with a notifier.

- The notifier manages the event queue.
    
- Advantage: Parallelism. The application isn't "stuck" in a loop; it only responds when the notifier signals an event.
    

> [!question] FAQ
> 
> **Q: What are the two main paradigms for programming the application and controlling the dialogue?**
> 
> **A:** > 1. **Read-evaluation loop (Internal control):** A continuous loop inside the application that reads an event, evaluates it, processes it, and repeats.
> 
> 2. **Notification-based (External control):** The application registers callbacks with a notifier. When input is detected, the notifier triggers the relevant callback function.

### "Going with the Grain"

The choice of paradigm dictates how easy or hard it is to implement certain UI features.

- Modal Dialogue Box: (User must interact with it before doing anything else). Easy with Event-Loops; hard with Notification (requires many mode flags).
    
- Non-Modal Dialogue Box: (User can ignore it and work elsewhere). Hard with Event-Loops; easy with Notification (just add an extra handler).
    

> [!warning]
> 
> Implementation should not drive design! If you don't explicitly design the interface, the limitations of your chosen programming model will dictate the user experience.

## 4. Interaction Toolkits

Toolkits provide a layer of abstraction that links input and output into Interaction Objects (Widgets, Gadgets).

![[Pasted image 20260516003830.png]]
### Benefits of Toolkits

- Consistency: Provides a similar "look and feel" across applications.
    
- Object-Oriented: Buttons and menus are treated as objects with states and events.
    

> [!tip] HCI Principle: Error Prevention
> 
> A good programmer codes for Mouse Release rather than Mouse Press. This allows the user to move the pointer away if they realize they've made a mistake before letting go, facilitating error tolerance.

### Java Toolkits: AWT vs. Swing

- AWT (Abstract Window Toolkit): The original notification-based toolkit. Relied heavily on native calls.
    
- Swing: Built on top of AWT. It provided "wrapped" capabilities to support MVC (Model-View-Controller) architecture, allowing for much richer views.

## 5. User Interface Management Systems (UIMS)

UIMS adds a level above toolkits to help even non-programmers design interfaces (e.g., Visual Basic).

### Core Conceptual Goal

The primary goal is the separation between application semantics (logic) and presentation.

> [!success] This improves:
> 
> - Portability: Runs on different systems.
>     
> - Reusability: Components can be reused to cut costs.
>     
> - Customizability: Both designers and users can tweak the UI (e.g., custom portals).
>

## 6. Conceptual Architectures

![[Pasted image 20260516004319.png]]

### The Seeheim Model

Divided into three logical components:

1. Presentation: What the user sees.
    
2. Dialogue Control: The interaction logic.
    
3. Application: The functional logic.
    

> [!important] The Bypass/Switch
> 
> In Seeheim, there is a Switch that allows the application to communicate directly with the presentation. This is required for Rapid Semantic Feedback.

> [!example] Feedback Types
> 
> - Lexical: Mouse movement.
>     
> - Syntactic: Menu highlights when hovering.
>     
> - Semantic: The sum of numbers changing in a spreadsheet. Semantic feedback is usually slow because it involves the application logic.
>     
> - Rapid Semantic Feedback: Highlighting a trash can _as_ a file is dragged over it (prediction/forecasting).
>     

### The Arch/Slinky Model

An expansion of Seeheim with 5 levels, including a "Functional Core Adaptor."

- "Slinky" Nature: Different layers can be "thicker" (more important) depending on the specific system or component.

## 7. Component Models: MVC vs. PAC

As systems became more object-oriented, monolithic models like Seeheim were replaced by smaller component models.

### MVC (Model-View-Controller)

![[Pasted image 20260516004631.png]]

- Model: Internal state.
    
- View: Rendering.
    
- Controller: Processes input.
    

> [!bug] The MVC Issue
> 
> MVC is a pipeline: Input -> Control -> Model -> View. However, in GUIs, input only has meaning in relation to the output. The controller needs to know _what_ was clicked, but only the View knows the layout. In practice, the controller must "talk" to the view, breaking the strict separation.

### PAC (Presentation-Abstraction-Control)

![[Pasted image 20260516004933.png]]

- Closer to the Seeheim spirit.
    
- Each PAC object is a self-contained unit.
    
- Cleaner than MVC: It manages hierarchies better because Control objects communicate with each other.
    
```mermaid
graph LR
    P[Presentation] --- C[Control]
    C --- A[Abstraction]
    C1[Control Sub-obj] --- C
```

> [!question] FAQ
> 
> **Q: How do the MVC and PAC models differ?**
> 
> **A:** > - **MVC:** Model (state), View (render), Controller (input). It is a pipeline, but separation often breaks because the controller needs context from the view.
> 
> - **PAC:** Abstraction (state), Presentation (I/O), Control (mediator). It manages hierarchy better and is "cleaner," though MVC is more common in practice (Java Swing).
>

## 8. Implementation Techniques & The Drift

### Techniques for Dialogue Controllers

- Menu Networks & State Transition Diagrams.
    
- Constraints: Instead of saying what _happens_, you define what should be true (e.g., ALV: Abstraction-Link-View).
    
- Graphical Specification: Drawing components and linking them with scripts (Visual Basic, Flash).
    

> [!danger] Graphical Specification Drawback
> 
> It suffers from the Local vs. Global problem. You see what is on one screen clearly, but it is hard to "see" the paths and flow through the entire system.

### The Drift of Dialogue Control

Dialogue control has shifted over time:

1. Internal Control: Read-evaluation loop (Terminal age).
    
2. External Control: Toolkit-based, independent of semantics.
    
3. Presentation Control: Driven by graphical specification.
